  规则 1：非核心文件清理
═══════════════════════════════════════════════════════

触发条件：每 2 次代码改动（迭代/重写）后，自动执行一次清理。

清理范围：
  ✅ 删除：临时修复脚本（如 _fix_*.py、_test_*.py、_verify.py）
  ✅ 删除：Python 缓存目录（__pycache__/ 及所有 .pyc 文件）
  ✅ 删除：被替代的旧版本文件（如旧版 JS/CSS 已不再引用）
  ❌ 保留：所有在 app.py / config.py 中引用到的核心文件
  ❌ 保留：data/ 目录下的所有数据文件
  ❌ 保留：日志文件（本文件、踩坑日志、工作日志）

核心文件清单（不可删除）：
  D:\2\app.py              — 后端主程序
  D:\2\config.py           — 配置
  D:\2\requirements.txt    — 依赖
  D:\2\run.bat             — 启动脚本
  D:\2\.env                — 环境变量
  D:\2\modules\            — 全部模块
  D:\2\static\             — 全部静态资源
  D:\2\data\               — 全部数据文件
  D:\2\全局复利踩坑日志.txt   — 踩坑记录
  D:\2\Codex工作日志.txt     — 工作记录
  D:\2\规矩日志.txt          — 本文件

═══════════════════════════════════════════════════════
  规则 2：运行后自检
═══════════════════════════════════════════════════════

每次写完代码并运行后，必须执行以下自检：

  1. 语法检查：py_compile 编译 Python 文件，确认无语法错误
  2. API 连通性：测试关键 API 端点（/api/status、/api/resumes/list 等）
  3. 前端资源：确认 JS/CSS 文件可正常加载（HTTP 200）
  4. 网页渲染：打开浏览器确认页面无控制台报错、WS 已连接

自检结果记录到 Codex工作日志.txt，自检失败记录到 全局复利踩坑日志.txt。

  规则 3：不要过度修复
═══════════════════════════════════════════════════════

  ❌ 当前指令没有让你修的问题，不要去修

  ✅ 有问题等用户下一条指令再处理

═══════════════════════════════════════════════════════
  规则 5：每次改动前必须备份
═══════════════════════════════════════════════════════

触发条件：每次修改任何项目文件之前，强制执行备份。

备份目标：D:\2\backups\
备份脚本：D:\2\scripts\backup.ps1

执行方式：
  powershell -ExecutionPolicy Bypass -File D:\2\scripts\backup.ps1 -Path <文件路径>

备份策略：
  ✅ 修改前备份：修改任何核心文件（app.py、v7.js、style.css、config.py 等）前必先备份
  ✅ 命名格式：<文件名>_<yyyyMMdd_HHmmss>.<扩展名>
  ✅ 保留规则：同一文件保留最近 5 个备份版本，旧的自动删除
  ❌ 不备份：data/ 目录下的数据文件（体积大且自动生成）
  ❌ 不备份：__pycache__、node_modules 等缓存/依赖目录

作用：
  - 防止一次代码失误导致连锁修 bug
  - 出问题时可以快速回滚到上一个正常版本
  - 对比备份版本快速定位哪次改动引入了问题

违规后果：
  - 如果因为没备份导致代码丢失/无法回滚 → 立即记录到 全局复利踩坑日志

═══════════════════════════════════════════════════════
  规则 6：禁止私自重写代码
═══════════════════════════════════════════════════════

触发条件：永远生效

核心原则：
  ❌ 不到万不得已，禁止重写（rewrite）任何文件
  ❌ 绝对禁止未经用户同意私自重写代码
  ❌ 即使发现代码有问题，也只能精确修补（patch），不能推倒重来

重写定义：
  - 删除大段代码后重新编写
  - 重构整个函数/模块
  - 用新实现替换旧实现（即使功能相同）

例外流程（必须执行）：
  如果确实需要重写，必须先向用户说明：
    1. 哪个文件需要重写
    2. 为什么不能修补只能重写
    3. 重写的风险和可能引入的新 bug
    4. 等待用户确认后才能操作

历史教训：
  v7.js 被反复重写导致：
  - 文件大小从 26KB → 13KB → 2KB（截断）
  - 引入 ||''' 三引号、单引号未转义、函数缺闭合括号等多次连锁 bug
  - 每次修一个 bug 引入新 bug，根源就是重写
  - 如果当时是精确修补而非重写，大量问题可以避免

违规后果：
  未经同意私自重写 → 立即记录到踩坑日志，并通知用户


══════════════════════════════════════════════
  规则 7：板块隔离 — 修 A 不动 B
══════════════════════════════════════════════
触发条件：永久生效
核心原则：
  ✅ 修改 bug 时，只改当前板块相关的代码
  ❌ 绝对禁止顺手"优化"或触碰其他板块
  ❌ 绝对禁止因为"看着不顺眼"去改无关代码

为什么：
  - 修 A 板块时碰了 B 板块 → B 出 bug
  - 修 B 又碰了 C → 连锁反应永无止境
  - 这是历史上最频繁的翻车原因

判断标准：
  改动的每一行代码，都必须能直接回答："这行不改，当前 bug 能修好吗？"
  答"能" → 这行不该动
  答"不能" → 可以动

示例：
  Bug: 证件照上传不工作
  ✅ 改 uploadPhoto 函数  ← 直接相关
  ✅ 改 /api/resume/photo  ← 直接相关
  ❌ 顺手改 Navbar 样式   ← 无关！
  ❌ 顺手重构 renderStep3  ← 无关！

违规后果：
  触碰其他板块导致新 bug → 立即记录到踩坑日志
