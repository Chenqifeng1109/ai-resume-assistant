  规则 1：非核心文件清理
═══════════════════════════════════════════════════════

触发条件：每 2 次代码改动（迭代/重写）后，自动执行一次清理。

清理范围：
  ✅ 删除：临时修复脚本（如 _fix_*.py、_test_*.py、_verify.py）
  ✅ 删除：Python 缓存目录（__pycache__/ 及所有 .pyc 文件）
  ✅ 删除：被替代的旧版本文件（如旧版 JS/CSS 已不再引用）
  ❌ 保留：所有在 app.py / config.py 中引用到的核心文件
  ❌ 保留：data/ 目录下的所有数据文件
  ❌ 保留：日志文件（本文件、踩坑日志、工作日志）

核心文件清单（不可删除）：
  D:\2\app.py              — 后端主程序
  D:\2\config.py           — 配置
  D:\2\requirements.txt    — 依赖
  D:\2\run.bat             — 启动脚本
  D:\2\.env                — 环境变量
  D:\2\modules\            — 全部模块
  D:\2\static\             — 全部静态资源
  D:\2\data\               — 全部数据文件
  D:\2\全局复利踩坑日志.txt   — 踩坑记录
  D:\2\Codex工作日志.txt     — 工作记录
  D:\2\规矩日志.txt          — 本文件

═══════════════════════════════════════════════════════
  规则 2：运行后自检
═══════════════════════════════════════════════════════

每次写完代码并运行后，必须执行以下自检：

  1. 语法检查：py_compile 编译 Python 文件，确认无语法错误
  2. API 连通性：测试关键 API 端点（/api/status、/api/resumes/list 等）
  3. 前端资源：确认 JS/CSS 文件可正常加载（HTTP 200）
  4. 网页渲染：打开浏览器确认页面无控制台报错、WS 已连接

自检结果记录到 Codex工作日志.txt，自检失败记录到 全局复利踩坑日志.txt。

═══════════════════════════════════════════════════════
  规则 3：不要过度修复
═══════════════════════════════════════════════════════

  ❌ 当前指令没有让你修的问题，不要去修
  ❌ 自检时发现的问题，只记录不修复（除非当前指令要求）
  ✅ 有问题等用户下一条指令再处理
  ✅ 自检发现的错误 → 记录到踩坑日志即可

═══════════════════════════════════════════════════════
  规则 5：每次改动前必须备份
═══════════════════════════════════════════════════════

触发条件：每次修改任何项目文件之前，强制执行备份。

备份目标：D:\2\backups\
备份脚本：D:\2\scripts\backup.ps1

执行方式：
  powershell -ExecutionPolicy Bypass -File D:\2\scripts\backup.ps1 -Path <文件路径>

备份策略：
  ✅ 修改前备份：修改任何核心文件（app.py、v7.js、style.css、config.py 等）前必先备份
  ✅ 命名格式：<文件名>_<yyyyMMdd_HHmmss>.<扩展名>
  ✅ 保留规则：同一文件保留最近 5 个备份版本，旧的自动删除
  ❌ 不备份：data/ 目录下的数据文件（体积大且自动生成）
  ❌ 不备份：__pycache__、node_modules 等缓存/依赖目录

作用：
  - 防止一次代码失误导致连锁修 bug
  - 出问题时可以快速回滚到上一个正常版本
  - 对比备份版本快速定位哪次改动引入了问题

违规后果：
  - 如果因为没备份导致代码丢失/无法回滚 → 立即记录到 全局复利踩坑日志

═══════════════════════════════════════════════════════
  规则 6：禁止私自重写代码
═══════════════════════════════════════════════════════

触发条件：永远生效

核心原则：
  ❌ 不到万不得已，禁止重写（rewrite）任何文件
  ❌ 绝对禁止未经用户同意私自重写代码
  ❌ 即使发现代码有问题，也只能精确修补（patch），不能推倒重来

重写定义：
  - 删除大段代码后重新编写
  - 重构整个函数/模块
  - 用新实现替换旧实现（即使功能相同）

例外流程（必须执行）：
  如果确实需要重写，必须先向用户说明：
    1. 哪个文件需要重写
    2. 为什么不能修补只能重写
    3. 重写的风险和可能引入的新 bug
    4. 等待用户确认后才能操作

历史教训：
  v7.js 被反复重写导致：
  - 文件大小从 26KB → 13KB → 2KB（截断）
  - 引入 ||''' 三引号、单引号未转义、函数缺闭合括号等多次连锁 bug
  - 每次修一个 bug 引入新 bug，根源就是重写
  - 如果当时是精确修补而非重写，大量问题可以避免

违规后果：
  未经同意私自重写 → 立即记录到踩坑日志，并通知用户


══════════════════════════════════════════════
  规则 7：板块隔离 — 修 A 不动 B
══════════════════════════════════════════════
触发条件：永久生效
核心原则：
  ✅ 修改 bug 时，只改当前板块相关的代码
  ❌ 绝对禁止顺手"优化"或触碰其他板块
  ❌ 绝对禁止因为"看着不顺眼"去改无关代码

为什么：
  - 修 A 板块时碰了 B 板块 → B 出 bug
  - 修 B 又碰了 C → 连锁反应永无止境
  - 这是历史上最频繁的翻车原因

判断标准：
  改动的每一行代码，都必须能直接回答："这行不改，当前 bug 能修好吗？"
  答"能" → 这行不该动
  答"不能" → 可以动

示例：
  Bug: 证件照上传不工作
  ✅ 改 uploadPhoto 函数  ← 直接相关
  ✅ 改 /api/resume/photo  ← 直接相关
  ❌ 顺手改 Navbar 样式   ← 无关！
  ❌ 顺手重构 renderStep3  ← 无关！

违规后果：
  触碰其他板块导致新 bug → 立即记录到踩坑日志
[2026-07-14] 教学协作规则
每次代码优化除说明结果外，还要用大白话解释：专业名词是什么、为什么需要、具体改了什么、给用户一个简短复习题；默认用户是 Python 初学者，使用生活类比并逐步增加难度。

══════════════════════════════════════════════
  规则 8：固定教学汇报格式
══════════════════════════════════════════════
建立时间：2026-07-16
触发条件：以后每次项目优化、修复、重构、测试或阶段总结后永久生效。

核心要求：
  - 使用清楚的大标题分区，采用“结论在前、细节在后”的顺序。
  - 默认用户是技术初学者；先用大白话和生活类比，再补充必要专业名词。
  - 不只汇报“做完了什么”，还必须让用户知道“以前怎样、现在怎样、为什么这样更好”。
  - 进度、结构、测试和下一步必须明确，避免只给一段笼统总结。

固定栏目与顺序：
  1. 当前进度
     - 使用文本进度条展示准备/清理进度与正式地基或总优化进度。
     - 标明百分比、当前阶段，以及已经完成的模块。
     - 示例：正式地基：[██████░░░░] 约56%。

  2. 本次结构变化
     - 用“以前 / 现在”的树状结构对比代码职责。
     - 列出新增、修改或删除的文件，以及关键文件修改前后的行数。
     - 如果没有结构变化，明确写“本次没有调整结构”。

  3. 你学到的概念
     - 逐个解释本次出现的 Router、Service、线程池、数据库等概念。
     - 每个概念包含：它是什么、负责什么、为什么需要、对应的一小段真实代码。
     - 必须追加一句生活化类比，帮助用户形成直觉。

  4. 测试结果
     - 使用逐条清单，不得只写“测试通过”。
     - 列出语法、路由数量、重复路由、成功路径、错误路径、首页、静态资源、WebSocket、测试残留等实际结果。
     - 失败和自纠错也要如实说明。

  5. 备份
     - 列出本次修改前的备份文件，尽量提供可点击文件链接。

  6. 发现但暂未修改的问题
     - 只报告本次发现但不在当前范围内的问题，解释可能影响和计划处理阶段。
     - 严格遵守“不要过度修复”，未授权不得顺手修改。
     - 没有新发现时写“本次没有发现新的范围外问题”。

  7. 测试你
     - 每完成一个学习部分都给2至4道简短题目。
     - 题目围绕本次实际改动，检查用户是否理解职责、原因和遗漏后的结果。
     - 先让用户作答；下一轮批改并把错题用于复习，不提前直接公布全部答案。

  8. 下一步
     - 用一句话说明下一批准备处理什么、为什么按这个顺序处理。
     - 如果必须先完成小测或等待用户确认，要明确写出。

排版要求：
  - 优先使用短段落、项目符号、编号、文本进度条和小型代码块。
  - 文件名、接口地址和关键函数使用行内代码标识。
  - 避免密集术语、超长段落和只面向专业开发者的表达。
  - 某个栏目确实不适用时可以简写，但标题应保留并说明“不适用”，保证每次汇报结构稳定。

本规则来源：用户提供的四张既有汇报截图；后续 Codex 开始项目工作时应先读取本文件，并按本格式回复。
══════════════════════════════════════════════
  规则 9：学习测试迁移与通过闸门
══════════════════════════════════════════════
建立时间：2026-07-26
触发条件：所有学习阶段的小测、复测和周测

1. 禁止直接复用刚讲过的代码、变量名、字段名和业务案例。测试必须改用同结构的新场景、新数据和新命名；没有现成题时，现场编写迁移题。
2. 默认测试难度为 5/10，重点检查迁移理解、错误判断和实际应用，不考死记原项目代码。
3. 每次按 100 分给出具体总分和分项得分。默认维度为：概念准确 40 分、推理过程 25 分、迁移应用 20 分、专业表达 15 分。
4. 75 分为通过线。低于 75 分时，必须重新教学当前部分，不得进入下一主题。
5. 出现错题时，无论总分是否达到 75 分，都要先讲清原题错在哪里、正确逻辑是什么，再用不同业务场景进行一轮变式复测。错题最多复测一轮；如果变式复测仍有小错误，只降低该知识点的掌握评级并讲清正确答案，不再针对复测错误继续出题，避免无限循环。若暴露出根本性理解错误，再由整体分数和教师判断决定是否重学当前部分。
6. 不提前泄露测试答案。评分必须明确说明扣分点、当前掌握程度和能否继续。
